# RecruitmentGuard

## Project status

**Stage:** v2.1 Evidence Operations Layer complete — synthetic benchmark, guarded evidence workflow, review queue, audit export, reproducibility verifier, and CI are in place.

RecruitmentGuard is a hackathon prototype for a **single-role candidate evidence brief**. It is designed for Priya, a recruiter at a Series B fintech startup who must prepare a hiring-manager briefing from a job description, résumé, interview transcript, and optional assessment.

## Who has this problem

Priya is closing a Backend Engineer requisition that has been open for six weeks. She needs to screen multiple candidates quickly and build an evidence-based case that a hiring manager can review.

## The bottleneck

The résumé, interview transcript, and assessment were created at different times and for different purposes. Under time pressure, a recruiter can miss material inconsistencies, such as a résumé claiming that a candidate led a team of eight while the interview describes mostly solo work. Missing or stale assessment evidence can also be silently omitted from a smooth summary.

## Why an agent

A plain summarization prompt tends to produce a coherent narrative even when sources disagree. RecruitmentGuard instead binds claims to exact source spans, extracts comparable facts into a fixed schema, checks contradictions and evidence freshness deterministically, and pauses for a human review whenever a blocking finding exists.

The system **does not make a hire/no-hire decision**. It produces an evidence brief for the recruiter and hiring manager; the human decision remains outside the system.

## Fixed sprint scope

The implementation uses one shared Backend Engineer job description and 12 synthetic candidate packets: three planted cases and nine clean controls. It contains two fair comparison paths:

| Path | Description |
|---|---|
| `baseline/` | A single-prompt summarizer with no extraction, validation, or checkpoint |
| `guarded/` | Structured extraction → deterministic validation → human checkpoint → evidence-bound brief |

The three planted cases are a team-size/ownership contradiction, a claimed-skill versus demonstrated-depth contradiction, and stale or missing assessment evidence. The primary evaluation metric is the number of planted issues surfaced out of three. Secondary metrics are guarded false positives across nine clean packets and per-packet runtime/token cost.

## Safety and data boundaries

All candidate packets are synthetic. The prototype does not connect to an ATS, email, or any external system that could take a consequential action. It produces no score, rank, or recommendation, and a flagged brief cannot be finalized until a human resolution is recorded.

## Changelog discipline

`CHANGELOG.md` is maintained continuously. Every sprint or meaningful behavior change gets an entry in the same change set before the next implementation step. Metrics are added only after they are generated by the evaluation harness; estimated or backfilled results are not permitted.

## Improvement Changelog

The full running log is in [`CHANGELOG.md`](CHANGELOG.md). The highest-leverage iterations were:

| Iteration | Failure addressed | Evidence and decision |
|---|---|---|
| Baseline → guarded pipeline | Smooth summaries hid contradictions and stale evidence. | Same 12 packets: baseline surfaced `0/3`; guarded surfaced `3/3`; guarded false positives were `0/9`. Kept structured extraction, deterministic validation, and human checkpointing. |
| Evaluation scoring correction | The baseline disclaimer was mistakenly counted as a finding. | Scoring was restricted to the summary section and the corrected result remained `0/3` versus `3/3`. Kept the correction. |
| Ownership heuristic refinement | Broad ownership matching risked false blocking on ambiguous shared work. | V2 reached `5/5` recall, `0` blocking false positives, and `100%` citation fidelity. Kept conservative review-only treatment for ambiguity. |
| Live provenance hardening | A live model returned a valid quote with an incorrect offset. | The run failed closed; exact unique spans are now repairable, ambiguous spans remain rejected. Live quality remains unclaimed until a complete run succeeds. |

**Main failure mode:** a confident narrative can hide a contradiction or unverified citation. **Hot take:** in consequential workflows, the best agent output is often a precisely cited reason to pause—not a confident recommendation.

## Engineering guide

The design uses only the capabilities required by the failure mode. Better context is provided by structured extraction with a fixed taxonomy and exact source spans. Verification is provided by deterministic subject comparison and assessment freshness checks. A file-based human checkpoint is used because hiring evidence can materially affect a person; the system cannot finalize flagged output until a recruiter records a resolution. Memory, multi-agent orchestration, and external tools are intentionally omitted because the task is a single-packet workflow with no cross-run state and no safe need for autonomous external action.

The architecture is deliberately sequential:

```text
data/packet_NN
      |
      +--> baseline/       single-prompt summary
      |
      +--> extraction/     structured CV + transcript facts
                |
          validator/       deterministic contradictions + evidence gaps
                |
        pending_review/    human resolution when blocked
                |
          checkpoint/      evidence-bound final brief
                |
          trajectories/    stage-by-stage readable audit record
```

## Evidence Operations workflow (v2.1)

The operator-facing workflow accepts a single packet directory, a directory containing `packet_*` directories, or a CSV/JSON manifest. It imports the packet without ATS credentials, runs the deterministic evidence extraction and validation path, creates attributable review items for blocking findings, and writes a traceable audit record. Clean packets receive `brief.md`; packets with blocking findings receive only `audit.json` and remain `pending_review`.

```bash
python3 -m workflow.run data_ops/packet_001 \\
  --output-root workflow_output \\
  --as-of 2026-08-30 \\
  --owner recruiter
```

A CSV or JSON manifest must include `packet_path`, `packet_dir`, or `path` for each row. The output contains `run.json` plus one directory per packet. Use `--due-at` to assign a review deadline, then resolve a blocking packet with an attributable note:

```bash
python3 -m workflow.run --output-root workflow_output \\
  --resolve-packet 004 \\
  --actor recruiter \\
  --resolution-note "Recruiter confirmed the assessment was refreshed."
```

The workflow treats withdrawn or inactive consent as blocking and refuses reviewer override; it never emits a hiring score, ranking, recommendation, or ATS write-back action.

## Reliability insight

> **In consequential workflows, the best agent output is often a precisely cited reason to pause—not a confident recommendation.**

This became concrete during live evaluation: the model returned a valid quoted span with an incorrect character offset. The system rejected the unverified citation, then added a deterministic repair only for exact unique matches and continued to fail closed on ambiguity. The lesson is to score output semantics, preserve provenance, and make uncertainty operational before narrative synthesis.
