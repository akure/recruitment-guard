# RecruitmentGuard V2.0 release notes

## Release scope

RecruitmentGuard V2.0 is a configurable evidence-review prototype for modern hiring workflows. It supports three fictional hiring contexts—startup, enterprise, and small team—and four role families. It uses realistic-but-fictional job descriptions, resumes, interview transcripts, assessments, and benchmark annotations.

The intended user is a recruiter or hiring reviewer who needs a traceable briefing from imperfect hiring evidence. The system organizes what is supported, conflicting, stale, ambiguous, or uncorroborated and asks for human review where the evidence requires it.

> V2.0 does not rank candidates, assign hireability scores, infer protected traits, or make hire/no-hire recommendations.

## What is included

| Area | V2.0 capability |
|---|---|
| Dataset | 12 synthetic packets across 3 hiring profiles and 4 role families |
| Extraction | Profile-aware JD requirements and typed CV/transcript evidence |
| Provenance | Exact source text, offsets, evidence kind, evidence quality, confidence, corroboration hints |
| Validation | Requirement coverage, conflicting evidence, missing/stale assessments, timeline inconsistency, ambiguity, and uncorroborated evidence |
| Human review | Blocking findings create pending-review state and prevent final brief generation |
| Briefs | Supported evidence, requirement gaps, conflicts, stale evidence, ambiguity, uncorroborated evidence, and reviewer questions |
| Evaluation | Cross-context finding recall, blocking false positives, citation fidelity, and reviewer-burden metrics |
| Reproducibility | Deterministic mock mode with no credentials required |

## Architecture

The release uses one configurable pipeline rather than three separate profile implementations:

```text
data_v2 packet
      |
      +--> profile + role configuration
      |
      +--> v2 extraction: requirements + provenance-rich evidence
                    |
              deterministic validation
                    |
       +------------+------------+
       |                         |
  final brief              pending review
  if non-blocking           if blocking
       |                         |
       +-------- human resolution
```

V1 remains available and unchanged under the `v1.0.0` tag. V2 uses additive schemas and `data_v2/` so the original benchmark remains a stable comparison point.

## Measured cross-context evaluation

The committed evaluation ran on all 12 packets: four startup, four enterprise, and four small-team cases.

| Metric | Overall result |
|---|---:|
| Finding recall | 5/5 — 100% |
| Blocking false positives | 0 |
| Citation fidelity | 100% |
| Packets requiring human review | 5/12 — 41.67% |
| Blocking findings | 5 |
| Average reviewer questions per packet | 2.00 |
| Average blocking findings per review packet | 1.00 |

| Hiring profile | Packets | Finding recall | Review rate | Citation fidelity |
|---|---:|---:|---:|---:|
| Startup | 4 | 1/1 — 100% | 25% | 100% |
| Enterprise | 4 | 1/1 — 100% | 25% | 100% |
| Small team | 4 | 3/3 — 100% | 75% | 100% |

These values are generated by `eval/run_v2.py` and stored in `eval/v2_metrics.md` and `eval/v2_results.json`. They measure evidence surfacing and review workload, not candidate quality or hiring outcomes.

## Reproduce the release

```bash
python3 scripts/generate_data_v2.py
python3 -m extraction.run_v2
python3 -m checkpoint.v2_runner
python3 eval/run_v2.py
python3 -m unittest discover -s tests -v
```

The expected full-suite result is **28/28 tests passed**. The expected evaluation result is **5/5 finding recall, 0 blocking false positives, and 100% citation fidelity** in deterministic mock mode. See [`REPRODUCE.md`](../REPRODUCE.md) for the complete clean-checkout procedure.

## Known limitations

The benchmark is intentionally compact and fictional. Live-model quality, token cost, broader role coverage, and independent human usefulness ratings are not claimed by this release. The small-team profile has the highest observed review rate in this benchmark; that may reflect the policy emphasis or the current packet composition and should be tested with a larger benchmark before product conclusions are drawn.
